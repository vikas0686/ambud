# Ambud MVP

The MVP is the smallest version of Ambud that is genuinely useful — not
a demo, not a tech-preview, but something you'd actually reach for to
deploy a container to one of a couple of spare machines instead of SSHing
in and running `docker run` by hand.

It is reached at the end of **[Phase 5](ROADMAP.md#phase-5--container-scheduling)**
of the roadmap. Phases 0–5 are not optional prerequisites bolted onto the
MVP — they *are* the MVP, built incrementally so each step is runnable on
its own (see [`ROADMAP.md`](ROADMAP.md) for the full breakdown).

**Every capability below must be usable from the Web UI, by clicking
alone, with no terminal open** — not only via `ambudctl`. The CLI is a
first-class peer client (scripting, automation, low-level debugging),
not the primary way an operator is expected to use Ambud; see
[`ARCHITECTURE.md`](ARCHITECTURE.md)'s design principle on the UI having
zero special access and zero missing capability relative to the CLI. The
Web UI at MVP stage is plain and functional, not visually polished — see
[`ROADMAP.md`](ROADMAP.md)'s note on where dedicated UI/UX design work
fits, deliberately after the MVP, not before it.

## What the MVP must do

1. **Install Ambud on a Linux machine.** A built binary (or, at MVP
   stage, a documented `go build` + systemd unit — see
   [`DEVELOPMENT.md`](DEVELOPMENT.md)) — no packaging polish required
   yet, but the steps must be written down and reproducible.
2. **Start an Ambud node agent.** `ambud-agent` runs as a systemd
   service on that machine.
3. **Register the node with a control plane.** Using a join token
   generated by `ambudctl`, the agent registers itself on first start.
4. **See the node from the control plane.** `ambudctl node list` shows
   it.
5. **See CPU/RAM/disk information.** Reported by the agent on every
   heartbeat, visible via `ambudctl node list` / `ambudctl node describe`.
6. **Deploy a container to the node.** `ambudctl deploy <image>` creates
   a workload; the agent reconciles and starts it.
7. **Start/stop/restart the container.** `ambudctl start|stop|restart
   <workload>`.
8. **View basic container status.** `ambudctl ps` shows running/exited/
   crash-looping state per workload, per node.
9. **Support adding a second machine.** A second `ambud-agent`, on
   different hardware, joins the same control plane and shows up
   alongside the first.
10. **Deploy a workload to one of the available machines.** No node
    specified — the scheduler picks based on available resources.

Each of these maps directly to a roadmap phase:

| MVP capability | Roadmap phase |
|---|---|
| 1–2 (install, start agent) | Phase 0–2 |
| 3–5 (register, list, resources) | Phase 3 |
| 6–8 (deploy, lifecycle, status) | Phase 3 |
| 9 (second machine) | Phase 4 |
| 10 (scheduled placement) | Phase 5 |

The Web UI itself is scaffolded in Phase 0, gains its first real screens
(node list, deploy form) in Phase 3 alongside the control-plane API, and
reaches full functional parity with the CLI — every one of the 10
capabilities above clickable, not just scriptable — by the end of Phase
5. It is not a phase-8-or-later addition; see
[`ARCHITECTURE.md`](ARCHITECTURE.md) and [`ROADMAP.md`](ROADMAP.md) for
the phase-by-phase detail.

## What the MVP deliberately does not include

This list matters as much as the capability list above — it's the
guardrail against turning the MVP into a Kubernetes clone before it ever
ships.

- **No networking beyond what's needed to reach the control plane.**
  Cross-node container networking, host-port exposure, and service
  discovery are [Phase 6](ROADMAP.md#phase-6--networking) — after the
  MVP. In the MVP, "deploy a container" does not promise you can `curl`
  it from another machine yet.
- **No persistent storage.** Volumes are [Phase 7](ROADMAP.md#phase-7--storage).
  MVP containers are stateless; data is lost on container removal.
- **No monitoring dashboard, no metrics history, no Prometheus
  integration.** [Phase 8](ROADMAP.md#phase-8--monitoring). The MVP
  shows *live* resource snapshots (needed for scheduling anyway), not
  trends over time.
- **No user authentication.** [Phase 9](ROADMAP.md#phase-9--authentication--api-hardening).
  The MVP's control-plane API is trusted-LAN-only — document this
  loudly, do not deploy an MVP-stage cluster on an untrusted network.
- **No TLS, no mTLS, no production hardening.** [Phase 10](ROADMAP.md#phase-10--production-hardening).
  MVP is for a trusted home network, explicitly not for anything
  internet-facing.
- **No smart scheduling.** "Most free RAM wins" is the entire algorithm
  — no bin-packing, no priorities, no affinity rules.
- **No UI/UX design polish.** The Web UI is required and fully
  functional at MVP stage (see above) but is not visually designed —
  plain forms, tables, and buttons, no design system, no onboarding
  flow, no empty-state illustrations. Functional parity with the CLI is
  the MVP bar; making it feel like a polished product is real,
  intentional, later work (see [`ROADMAP.md`](ROADMAP.md)).
- **No Kubernetes-level anything**: no CRDs, no YAML manifests as an API
  surface, no controllers-for-controllers, no operators. A workload is
  "an image plus resource requests," full stop.

## Why this is the right MVP line

The MVP stops exactly at the point where Ambud becomes a genuine
multi-node platform (capability 10) rather than a fancy single-machine
Docker wrapper (capabilities 1–8 alone) — and not one step further. Every
capability past #10 (networking, storage, monitoring, auth, hardening)
is real and necessary before anyone should run this unattended, but none
of them are required to prove the core thesis: *a control plane that
knows about multiple real machines and can place a workload on one of
them without the operator doing the bookkeeping by hand.*

If you can demo capabilities 1–10 on your own hardware — the old Windows
PC (now running Linux) as node 1, your dev machine or a second spare box
as node 2 — Ambud has proven its reason for existing.

## After the MVP

Continue straight into [Phase 6](ROADMAP.md#phase-6--networking) through
[Phase 10](ROADMAP.md#phase-10--production-hardening) in
[`ROADMAP.md`](ROADMAP.md). Nothing about the MVP needs to be
re-architected to support those phases — they build on it, per the
[architecture](ARCHITECTURE.md)'s interfaces (`Scheduler`, `internal/
runtime`) being designed for exactly this kind of extension from the
start.
